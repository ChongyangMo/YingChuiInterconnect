# 生成 Mac 更新包

双击本目录的 `生成Mac更新包.command`，确认自动建议的下一版本并填写更新说明。构建号自动递增。脚本编译、签名、生成更新包，然后上传到部署工具的鹰锤电脑端；只有服务器回执与独立版本查询一致才显示上传完成。

上传后是待发布版本。用户在部署工具中点击一次“发布”，兼容的新版 Mac 客户端便会在启动时及每 300 秒检查、自动下载，并在空闲时安装和重新启动。无需选择设备或推送。生成器不会替用户发布版本或部署服务器。

## 首次切换

先发布配套业务后端和部署工具，再发布包含自动更新实现的客户端。旧客户端需要完成一次过渡安装；之后发布更高构建，才能验收完整自动升级。后台设备页的自动更新能力必须来自实际客户端心跳，不能靠后台改标签启用。

公开更新不依赖登录，使用当前应用架构与真实系统版本选择兼容版本。登录只用于设备管理回报。回传、现有连接、显示器恢复、账户操作、未保存编辑和模态操作都会延期安装；应用监听服务本身不会阻止更新。下载可以继续，空闲后自动恢复安装，安装前重新确认固定版本仍已发布。撤回、验签失败或请求异常均明确报错；没有新版是正常状态。

应用拥有唯一的 300 秒检查调度器和可取消的安装准备流程。因此 Sparkle 自身的定时检查与自动安装开关保持关闭，应用配置的 `automatic_updates=true` 对应主工程实际实现，并非仅修改框架开关。Sparkle 继续负责归档验签、替换应用及重启；系统如要求授权，仍需用户完成原生授权。

## 上传与重试

上传入口是 `POST https://deploy.chongyang.asia/api/yingchui-mac/ingest`，发送原始更新包。旧服务未支持新契约时明确报错并保留原包，不回退到旧上传即发布接口。

上传失败后，双击 `重试上传更新包.command`，或再次打开生成入口，即可重试原包，不重新编译或增加版本。同包由服务器按签名内容去重。已撤回或内容冲突会明确报错。每个包旁的 `.upload.json` 保存上传状态和校验摘要，不含密钥。

指定已有包重试：

```sh
/usr/bin/python3 scripts/mac-updates/build_update.py --upload-only /实际路径/更新包.ycu
```

只提供更新说明即可自动计算版本、打包和上传：

```sh
/usr/bin/python3 scripts/mac-updates/build_update.py --notes '填写本次更新内容'
```

必要时可追加 `--version` 和 `--build`，两个值都必须高于真实历史。若存在待重试上传，先完成原包上传，不能用新版本掩盖失败。全程文件锁阻止并行打包；已有终端占锁时应先正常结束该任务。

## 版本与签名

版本写入应用的 `CFBundleShortVersionString` 和包内 `app_version`，构建号写入 `CFBundleVersion` 和 `app_build`，说明写入 `release_notes`。新包统一使用 `channel=unified`，不提供正式/测试选择。已签名的历史包、原始元数据和版本记录保持原样。

版本基于真实项目及成功历史递增；已占用或失败构建号不复用。成功记录原子保存到 `artifacts/mac-updates/release-history.json`。历史损坏、冲突或未提交时直接报错，不清空历史或回到旧版本。

制品位于 `artifacts/mac-updates/build-构建号/package/`，编译日志位于同一构建目录的 `build.log`。生成器使用隔离编译目录，不覆盖正在运行的应用。生成前检查实际编译应用已配置统一自动更新，再验证真实代码签名，并用本机钥匙串私钥签署归档和元数据。接收设备不需要私钥。

当前配置使用本机 Apple Development 证书。取消渠道区分不会赋予 Developer ID 签名或公证；现有开发签名包可在满足运行条件的机器验收，面向普通用户分发仍需配置实际的 Developer ID 签名和公证。不能伪造签名、公证或上传校验结果。

配置位于 `build-config.json`，包含架构、证书标识和已确认的上传地址及超时，不使用环境变量。底层脚本 `yingchui_mac_release.py` 固定生成统一更新包，并检查实际应用配置；保留官方 Sparkle 2.10.0 签名工具。
